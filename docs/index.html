How it works

The whole loop, in four gestures.

Two of them are yours, and each takes a few seconds. The two in between are Ponos's.

  1. 01 · you

    You write the ticket

    What you would tell a colleague, on your board — then you move it to Ready.

  2. 02 · Ponos

    Ponos does it

    While you do something else: a pull request on its own branch, a text written into the ticket, an action carried out.

  3. 03 · you

    You read, and answer in a word

    A question or a result reaches you — in the console, or on your phone. oui is a whole answer.

  4. 04 · Ponos

    He delivers

    Move it to Validated: the pull request is merged, the post is published — and only then is it Done.

Why hand it over

Three things it does that a to-do list does not.

Not only code

A pull request, or a text.

“Remove that header” comes back as a pull request on its own branch. “Draft the October newsletter” comes back written into the ticket. Same board, same gesture — the ticket decides which, not a setting.

You keep the hand

Nothing goes out without you.

No pull request is merged and nothing is published until you move the ticket to Validated. And it all runs on your machine, each ticket in a disposable worktree — your own checkout is never touched.

Installation

One command.

It installs the ticket-runner command, a timer that hands Ponos the ready tickets, and the console — then asks for what it needs.

$ curl -LsSf https://raw.githubusercontent.com/SalvadorCardona/ticket-runner/main/install.sh | sh

Then, the board

Share one Notion page with an integration and let it build the rest — or skip Notion with storage.mode = "markdown", and the board is a folder of files.

$ ticket-runner init https://www.notion.so/your-page --token ntn_…
$ ticket-runner doctor

What it needs

  • Linux, with systemd in the user session;
  • python3 ≥ 3.11 — standard library only, nothing to install;
  • git, Claude Code, and gh for pull requests.
